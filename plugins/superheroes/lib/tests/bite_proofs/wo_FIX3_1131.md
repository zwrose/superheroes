## BP-FIX3-1 — the unreadable-landing recovery branch (`test_record_result_sweep_recovery_reports_unreadable_landing`)

**Guarded element:** the `if landing_err is not None:` branch in
`plugins/superheroes/lib/round_driver.py:6333`, inside `_cmd_record_result_locked`'s
`sweep and (supersede or expect_sha256 is not None)` recovery loop.

**Axis it claims — truthfulness of the refusal, not merely its presence.** The refusal
(`sweep-supersede-unsupported`) fires either way; what this branch guarantees is that a slot whose
landing is *present but unreadable* produces a recovery entry naming the refusal reason and the
stored CAS token, and therefore that the no-recovery `detail` string ("no slot has both a stored
record and a pending landing that differs from the stored envelope") is never emitted while a
landing file is in fact sitting there. The `"no slot has both" not in out["detail"]` assertion is
the line that carries this axis.

**Elements covered by the one neutralization.** The branch is a single guarded element exercised
through the four constructible refusal shapes of `round_records._read_landing_envelope` —
`landing-ambiguous`, `landing-torn`, `envelope-stub-missing`, `schema-unknown` — one distinct
failure mode each (ambiguous slot / unparseable bytes / absent stub / unrecognised schema). All
four go red under the single neutralization below, so each shape has its own red; none stands as a
representative for another. The set's two remaining members are out of the red: `landing-missing`
is the carve-out this branch deliberately keeps skipping (see *Known limit* below), and
`bad-argument` is unreachable at this site because the loop already resolved the storage key
through `round_records.storage_key` before reaching the read.

**Neutralization** (targeted, reversible edit applied to the source, the test unedited; reverted by
the inverse edit — no `git checkout`, `git restore`, `git reset` or `git stash` was used at any
point):

```diff
-            if landing_err is not None:
+            if False:
```

This restores exactly the pre-fix behaviour: the refusal is discarded, `envelope` stays `None`,
`landing_token` is `None`, and the slot falls into the `not landing_readable` `continue`.

## Known limit of this record

The branch's `landing-missing` carve-out — the one reason that must still `continue` silently — is
**not separately neutralized here, and is recorded as unproven by this dispatch**. Reddening it
requires removing the `if landing_err == "landing-missing": continue` line and running
`test_record_result_sweep_recovery_omits_recorded_missing_slot_with_no_replacement` (F2), a test
outside the invocations WO-FIX3's per-order test-command budget enumerates. F2 is green on the
final state of this work, which is consistent with the carve-out holding but is not a proof that it
bites.
