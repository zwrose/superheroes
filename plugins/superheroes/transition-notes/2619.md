### Before you upgrade

- **After switching.** **An advisor marking an issue build-ready passes `--issue <n> --repo <owner/name>` to `issue_contract.py check-build-ready`; nothing else is owed by a caller.** See [Build-ready check: native blocker edges](#build-ready-check-native-blocker-edges).

### Build-ready check: native blocker edges

- **What a reader sees differently.** With `--issue` and `--repo`, `check-build-ready` reads the issue's native `blocked_by` edges in full. An open blocker refuses with `blocker-open` and names each one: `owner/name#n`, its title and its URL. A read that fails or comes back malformed refuses with `blockers-unreadable`, and so does `--issue` or `--repo` given alone or malformed; none of these is read as "no blockers". When the body check itself refuses, its own reason stays the reported one. Every result gains a `blockers` object with the keys `checked`, `open` and `detail`. A body-only call, with neither `--issue` nor `--repo`, reports `checked: false` and keeps its old verdict.
- **The new verb.** `issue_contract.py check-blockers --issue <n> --repo <owner/name>` reads the edges alone. Its result carries `ok`, `reason`, `blockers` and `advisory`. It always exits 0, so a caller reads the JSON result, never the exit status.
- **The doctrine.** Routing (marking an issue build-ready, sizing it, recommending it) and the launch's base-state check read the issue's native edges and name any open blocker. A sub-issue and each layer of a stack is read on its own issue. The body's prose about edges is never the source.
- Replacement. None: no key, token, argument or result shape is renamed or removed.
