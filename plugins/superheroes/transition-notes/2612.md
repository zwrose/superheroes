### Before you upgrade

- **After switching.** **The cloud check gains a start-copy part, and this release's setup text changes because the plugin's start hook changed, so paste the new setup text into the cloud environment once, as the setup stamp already asks.** See [Cloud check: the start hook's plugin copy is read back](#cloud-check-the-start-hooks-plugin-copy-is-read-back).

### Cloud check: the start hook's plugin copy is read back

- **What a reader sees differently.** The cloud session's start hook now records, in a cloud session only, each plugin file it opens at start and the plugin folder that file came from, and writes one `SUPERHEROES_START_COPY` export to the session's environment file, bound to the session's id. The check's `report` carries it as the optional field `startParts`: for each part the hook opened, a list of the copies it came from, each `{version, commit, sha256}`, or `null` when the session left no usable record. `startParts` is not in `REPORT_FIELDS`, so an older report stays readable.
- **The new part.** `judge` adds the result key `startPartsMatch` (`true`, `false` or `null`), right after `calibrationMatches`, and the failed-check marker records the part `start`. The check fails on `start` when any part the hook opened has other bytes than this machine's copy of it, the hook's own part is missing from the record, the record is `null` or malformed, or this machine's own start parts cannot be read. A copy of an older plugin version with identical bytes passes: the comparison is of bytes, not versions.
- **The three new sentences.** When the bytes differ: "The cloud session's start hook ran start code that differs from mine: `lib/core_md.py` from plugin 0.50.0 at commit 0123456789ab, and mine is 0.51.0." (one item for each differing part and copy). To fix it, paste the new setup text into the environment. When the record is missing or malformed: "The cloud session did not report which plugin copy its start hook ran, so I could not check its start code." with the same fix. When this machine's parts cannot be read: "I could not read my own plugin's start code, so I could not compare the cloud's start hook with it." To fix it, tell me so I can look at this machine's plugin copy. A passing check adds the bullet "Its start hook ran the same start code as mine."
- **The older-report paragraph.** A report from an older session with no `startParts` key is judged as before, with `startPartsMatch` `null`, and the message (pass or fail) adds the paragraph "The start parts were not read back: the cloud session's plugin is older than the one that reports them, so its start code was not checked."
- **What is not judged.** The SessionStart registration in `hooks/hooks.json` is read by the host, not by the hook, so it is not read back; an older registration that launches an older hook still fails the check, because that hook leaves no record.
- Replacement. None: no key, token, argument or result shape is renamed or removed.
