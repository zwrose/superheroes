What: The landing epic for cloud builders. Today every build runs on the owner's machine, so the number of builds that can run at once is bounded by that machine. After this epic, a project set up for the cloud runs its builds in cloud sessions by default, under the same order, review, vet and merge rules as a build on the owner's machine; the advisor launches, watches, answers, recovers and cleans up a cloud builder as it does a local one; and the owner places the reviewer pass and any outside-the-repository calibration by hand, once per project, renewing the pass when the gardening pass says to. Eight children land it, as the eight layers of one native stack whose feature issue is this epic, numbered by their position in it:
- **C1, the cloud lane (the seam).** The launcher starts a builder in a cloud session and records it as a lane like any other, marked "cloud", with nothing left on the owner's machine.
- **C2, the setting and the setup record.** The per-project cloud-builds setting, off by default, switched on and off as the board words it, and the record of a project's cloud setup that every later reader reads.
- **C3, the setup text and the pass command.** The block the owner pastes into the cloud environment, the cloud picking up the advisor's plugin version where the platform allows, the pass command, and the step that hands the pass to the reviewer in each cloud session.
- **C4, the setup sitting and the check session.** The advisor's setup message and the one short cloud session that proves a setup.
- **C5, where a build runs.** One routing step sends each build to the cloud or the owner's machine by the launch word, what the build needs, the project's setting and five readiness conditions, and the launch report says which went where and why.
- **C6, the builder's cloud path.** A builder in a cloud session announces itself, pushes often, runs every review seat through the reviewer pass, asks the advisor by a builder note, and parks a PR whose review a lapsed pass stopped.
- **C7, the advisor's side of a running cloud build.** The wave watch surfaces builder notes and the advisor answers directly; a stopped cloud builder is recovered at once from its pushed work; a parked PR is announced and sent back for review after the pass is renewed.
- **C8, cleanup and the reviewer pass's upkeep.** After a merge or close the advisor asks the builder to archive itself and the owner taps once; the gardening pass reports the pass's days left and says when to renew.

Consuming projects stay on today's behaviour until they adopt the release that carries the whole stack, and then until their owner sets a project up and switches cloud builds on.

**Register entries (quoted verbatim from docs/superheroes/cloud-builders-66a2e8/register.md; as the stack's feature issue, this body carries every entry, and each child's register-quote check runs on this body with that child's token):**

> **R1 — The cloud lane record.** The launcher starts a cloud builder as a lane of the same launch ledger, in the same batch machinery, with the same terminal outcomes (handback, park, refusal, died), and records on the lane its place, the cloud or the owner's machine, and the cloud session's identity: its id and the name the host lists it under. A cloud launch creates no worktree and leaves no process on the owner's machine that the build depends on, so the build carries on while that machine sleeps, and it pushes no launch branch to the repository: the cloud session starts from a commit the repository already has. Every surface that lists or counts lanes (`count`, the lane listing, the wave watch, the liveness sweep) shows a cloud lane as one lane with the word "cloud" beside it, and every reader that branches on a lane's process, transcript or heartbeat is checked for the new place, so no check written for a local lane reads a cloud lane as dead, stalled or clean by default. A cloud lane's liveness is read from its activity on GitHub (pushes to its branch, comments on its issue or PR) and, when that goes quiet, from the session's state as the platform reports it, never from a local process or transcript. The ledger is version-coupled, so the new facts ride as fields on the existing record kinds unless C1 shows a new kind is needed and says why. The field names, how the watch reads a cloud lane's activity, and how a cloud lane's terminal outcome is recorded with no local child process are decide-by: C1.

> **R2 — What a cloud launch carries.** A cloud launch carries the same composed order as a launch on the owner's machine: the launcher's compose output for that issue, with the same standing rulings verbatim and the same issue pointer, and nothing in the issue body, the review rules, the advisor's vet or the merge rules changes with the place. It adds only what a cloud builder needs to know about its place: that it runs in a cloud session, and the plugin version the advisor runs. The cloud builder states both in its intake comment and checks at intake that the plugin it runs is that version. On any difference it stops before building: it reports the mismatch on its issue with both versions and ends with the terminal outcome `refusal`, because it declines its launch premise and leaves nothing for an owner decision, which a park would ask for. The advisor then relaunches that build routed as a launch, with the version the builder reported standing as the cloud's plugin version, so the build runs on the owner's machine and the launch report names both versions. A cloud builder thus never builds on a copy of the plugin other than the advisor's. How the place and the version reach the builder is decide-by: C1; how a reported version enters the routing step is decide-by: C5.

> **R3 — The cloud setting and the setup record.** Each project has one cloud-builds setting, read and written only through `plugins/superheroes/lib/project_config.py`, off until the owner switches it on, and refused while the project has no passed check on the launching Claude account. Each passed check writes one setup record for the project and that Claude account, holding: the account it was made on; the cloud environment the owner made; the plugin version the setup text carries, and whether the cloud picks up the advisor's version by itself; a stamp of the outside-the-repository calibration the setup text placed; the date the reviewer pass lapses; and the date of the passed check. The pass command alone never moves the record's lapse date: a pass it makes is not yet in the cloud, and no reader takes its date as the pass's lapse date. The lapse date moves only when a cloud session confirms that the reviewer answers with the new pass, by a check run or by the session-start step reporting it, and that confirmation is what "renewed" means for sending parked PRs back. Every write to the record goes through one write path beside its reader. Switching the setting off keeps the record. The record holds no reviewer pass and no other secret. One reader in `plugins/superheroes/lib/` answers what the setting and the record say, and launch routing, the readiness check, the renewal send-back and the gardening pass call it and re-derive none of it. The setting's configure item (its number and slug), the record's shape and home, its write path, the calibration stamp's form, and how the setup learns which environment the owner made are decide-by: C2; how a cloud session's confirmation of a new pass is made and reaches that write path is decide-by: C3; any of them that would add an owner step the build board does not draw is raised as an owner call.

> **R4 — The reviewer pass.** The reviewer pass is made on the owner's machine by the pass command, from a sign-in to the independent reviewer kept apart from the owner's main one and with its self-renewal switched off, and the command puts it on the owner's clipboard and nowhere else the plugin writes. The owner pastes it into the cloud environment's settings, where any session started in that environment can read it. At the start of every cloud session, before any review seat runs, the plugin writes it into the reviewer's default sign-in location on the cloud machine, so the plugin's review dispatch runs there unchanged and never through the owner's main sign-in; no plugin file, setup text, setup record, comment or log holds the pass. The environment setting's name, how self-renewal is switched off, and how the session-start step runs are decide-by: C3.

> **R5 — Where a build runs, and the launch report.** One routing step in the launch path decides each build's place, so a launch and a recovery are routed alike. A build the advisor judges, from its order, to need something only the owner's machine has runs there whatever the setting or the launch word says, and every build of a project that keeps its Canon or its specs outside the repository is judged that way. Otherwise a launch word that names a place wins over the project's setting, and a build pointed at the cloud, by the setting or by a launch word, runs in the cloud only when all five readiness conditions hold: the reviewer pass is live, the project has a cloud setup on the launching Claude account, the cloud's plugin version equals the advisor's, the cloud's calibration matches the owner's machine, and the cloud platform can be reached; otherwise it runs on the owner's machine. A cloud launch that fails at the platform runs the build on the owner's machine with the unreachable reason. No build is ever held or dropped for the cloud. The launch report names every launched build under "In the cloud" or "On your machine", and each build that ran on the owner's machine although the setting or a launch word pointed it at the cloud carries exactly one of the build board's eight reasons, in the board's words, with its fix: You said "this one local"; It needs <what it needs>, which only your machine has; The reviewer pass has lapsed; There is no reviewer pass in the cloud environment; This project has no cloud setup on this Claude account; The cloud's plugin is <cloud version> and mine is <advisor version>; The cloud's calibration doesn't match this machine's; The cloud platform couldn't be reached. Each fix is a step the setup surfaces offer on request: new setup text, the pass command, a fresh check, or setup itself. The order the conditions are checked in, and which reason a launch with several false conditions reports, are decide-by: C5.

> **R6 — Messages between the advisor and a cloud builder.** The advisor reaches a running cloud builder by a direct message to the session its lane record names, which wakes an idle session; a cloud builder cannot message the advisor, so it reaches the advisor only by a comment on its lane's issue. A builder note opens with the line "Builder note for the advisor (cloud build).", asks its question, and says the builder is waiting; the builder then waits in-turn for the answer for the same time the review discipline's size rule gives a builder waiting on the advisor's reply, and with no answer it parks with its work pushed, and the note waits on the issue. The cloud builder's first comment on its issue opens with "Builder intake (cloud build)." and states the plugin version it runs and that its commits carry the cloud's own author name while the PR is under the owner's name. The advisor's wave watch reads each watched repository's issue comments once per tick, by a conditional request that costs nothing when nothing changed, and surfaces a new builder note on a watched lane's issue as an event that wakes the advisor, who answers by direct message; when the advisor is back after being away, it answers each waiting note and resumes each lane parked on one the same way. The archive request after a merge or a close travels by the same direct message. On a public repository these comments are public, as builder comments already are.

> **R7 — The review a cloud build carries.** A cloud build is reviewed under the review rules of the plugin release it runs, which this epic builds on: epic #1708's release, whose review record (that epic's register R1) and independence rule (its register R5) a cloud build follows unchanged, on every lane. Every independent review seat of a cloud build runs through the reviewer pass (R4); no seat is dropped or treated as second class for running in the cloud. A cloud build's PR carries its review record and receipts, as a local build's PR does, and nothing the vet needs exists only on the cloud machine. When the pass has lapsed so a review cannot run, the builder records that review as not run and parks the PR with its work pushed, its comment opening "Parked: the review did not run."; the PR then follows the review rules for a review that did not run, the owner's own ways past them included, and no session picks a reviewer from a maker's model family on its own. A review that finished before the pass lapsed stays as recorded, and the cloud is never stricter than the owner's machine. The advisor's notice of such a park tells the owner that renewing the pass lets the PR go back for review; a review that did not run for any other reason is reported as the review rules already say, with no advice to renew the pass.
