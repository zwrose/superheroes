Build board · review loop rework · #2185 · version 7

A review loop that finishes in a few rounds

One full-lane review, end to end, as it will work after this rework. Light and micro lanes follow the same cap and the same "only what changed" rule with their single reviewer.

Build session Independent reviewer You

Panel 1

Round 1: find everything once

The build session opens the PR and starts the review

A big change (over about 1,000 lines a reviewer has to read, when the PR can't practically be split) is cut into slices by size, not by folder. Moved-but-unchanged files, generated and lock files, and whole-file deletions don't count; tests and docs do. When in doubt, slices are cut smaller. Each slice gets its own code and test reviewer.

↓

Code reviewer
Test reviewer: attaches a break-it test to each finding it can prove that way, and writes break-it tests on touched risk areas as today: at most three per review, at least one per area while under that cap
Security + premortem: both join on any risk area, or when the risk is unclear, as today

Each reviewer lists what it actually read.

↓

The build session runs each break-it test on the unfixed code, exactly as written, and saves the output. It does not judge the result.

↓

Verifier grades each finding on its own, with the break-it test's output in hand where there is one

A break-it test passed on the unfixed code? If it really goes down the path the finding describes, the finding was wrong. If it never reaches that path, the test missed: the reviewer writes one better test. If that one also passes, the verifier decides on what it has.

↓

Synthesis groups findings with the same root cause, and marks any that repeat one from earlier in this PR

↓ big change only

Anything no slice reviewer read becomes a new slice, with the full set: code, test, and security + premortem on a risk area
Seams check: one reviewer reads the whole change for how the slices interact

Their findings go through the break-it run, the verifier and synthesis like any other. The premortem reviewer reads the whole change, never a slice, as today.

↓

Every finding names its kind of mistake and every place in the PR that has it

↓ after a confirmed Important or Critical

The reviewer who raised it writes what to look for: the kind of mistake, what it looks like, examples

↓

The build session fans out cheap subagents to search the whole repo, once

Hit inside the PR: becomes a finding and goes through the verifier.

Hit outside the PR: goes on the record's "Outside this PR" list. Never blocks, never a card for you.

Panel 2

The build session fixes

Fixes every copy of each confirmed finding, and commits each fix together with its break-it test

The build session never closes a finding; only the verifier can call one wrong. No separate fixer, no fix orders, no locked-down fixer sandbox.

Panel 3

Rounds 2 to 4: check the fixes

Fix auditor, per fix: is it right? did it break anything next to it? if this fix were wrong, would a test fail?
Scoped finder: new problems in the code the fix touched

The auditor also checks the committed break-it test is the one the reviewer wrote. Any change must be explained, and a change that weakens the test is undone.

A repeat of an earlier finding keeps its earlier outcome and stays visible in the record. If an old fix no longer holds, or the code behind an earlier "not a bug" ruling has changed and the bug is real now, it is a new finding.

The same fix fails its audit in two rounds in a row: one automatic recovery attempt, inside the 4 rounds. If it still fails, the session stops early and hands back the same way as at round 4 (panel 4). No stall menu, and nothing reaches you mid-review.

Panel 4

How a session stops

Nothing blocking left: the review hands the PR back.

Round 4 reached with something open, or a fix still stuck after its recovery attempt: it stops and hands back with what's open. No automatic extra round, and no new review session to keep going.

↓ the advisor sorts what's open and decides at the vet

Code quality only (craft): the advisor decides it and lists it for your veto. Never a question to you.

One extra round that only audits the last round's fixes: no panel, no new search. At most once per PR.
To you as a leftover, in your terms: what accepting it means, costs and risks (never a Critical)
Back to the builder to rethink the approach

Each of these choices, and what happened next, is counted at the gardening pass, so we can see whether the advisor is choosing well.

Panel 5

After handback

The advisor's vet checks the PR description's claims against the change, sorts the "Outside this PR" list (propose a follow-up, or dismiss with a reason) and writes READY or NOT-READY

↓ the PR comes back: a send-back, a fix leg, catching up with main, or a hand fix

A new session reviews only what changed since the last reviewed commit, with the same fix audit and scoped finder

A full panel runs only when the new change is itself over about 1,000 lines a reviewer has to read, or touches a risk area the PR hadn't touched before.

Your merge sheet: no "grounding seat not run" line any more

Panel 6

When something goes wrong

Includes four field reports from a consuming project on 0.46.2, folded into this rework.

A finding carried over from an abandoned session always ends with an outcome. If later commits show it fixed, it is settled as fixed; otherwise it goes back to the reviewers. It never sits with no outcome, blocking the record for good.

A layer in a stack is reviewed against the current head of the layer below. If the layer below has moved, the session catches up before it reviews, never against an old base.

One failed test run on unchanged code gets one re-run of the same check, recorded in the review record. A second failure stops the round, as today. A single flaky test never costs a new session.

A reviewer's break-it test that needs a small change to run (for example, a type error): the build session may change it and says why. If the auditor finds the change weakened the test, the change is undone and the reviewer who wrote it gets one try to correct it. Still open at the cap: handed back like anything else open. The review never ends "cannot certify" over it.

Panel 8

Gone after this rework

  • The separate fixer, its fix orders and its locked-down sandbox (and with it #2186)
  • The review running project tests in throwaway copies of the repo
  • A fresh full panel on every new review session
  • The 7-round cap, the 10-round ceiling, and a separate "park" state at the cap
  • The stall menu: a stuck fix hands back like the cap instead
  • Read-only review mode
  • The grounding reviewer, and its "not run" line
  • Splitting big changes by top-level folder
  • Code review for a project with no test command: setup asks for one

Not added: a final review pass, per-area specialist seating, a replay of past cases before release, a target number.

Panel 9

How we'll know it worked

  • The gardening-pass row (#2189): rounds and sessions per PR, reviewer tokens and minutes, CI minutes, findings by reviewer, and now how often each choice was made at the cap and what happened next. Read as a trend; no target, never a gate.
  • Escape logging (#2190): every bug that gets through names what would have caught it.
  • Two revisit checks at each gardening pass: a false PR claim that got past the vet reopens the grounding reviewer's removal, and security and premortem still looking expensive for what they find reopens their seating.
  • The core loop ships first; slicing big changes, the sweep for copies of a bug, and the outside-this-PR list may follow in a later release.
